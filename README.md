# Soccer Outlook

A week of soccer at a glance, judged against the streaming services you have.

**Live page:** https://caparomula.github.io/soccer-outlook/

The page focuses on the rolling next 24 hours, including live matches. Claude researches storylines and short-range context; later fixtures stay in a collapsed section. Match counts, cards and service totals use the same 24-hour window. Each match shows every US broadcaster ESPN lists, team form and table position, and a details panel with scorers, venue, a calendar link and the league table.

If the page is useful to you, **Buy me a coffee** at the right end of the bar under the title (a cup on a phone) goes to the owner's Buy Me a Coffee page, the same one `.github/FUNDING.yml` gives the repository's Sponsor button.

## Your lineup

Tap **Lineup** in the bar under the title and tap the services you have and the competitions you want. The bar, with the **On my services** / **Everything** toggle and the coffee link, stays at the top of the window as you scroll, and changing the view or the lineup from there keeps your place in the schedule (the match at the top of the window stays put; one the change hides gives way to the next one shown). Where the bar's controls would not fit on one line (a narrow phone, a larger text size), Lineup shows its icon alone. Every match is then judged against your lineup; the choice stays in your browser. Broadcasters and leagues each have **Select all** and **Clear all** controls. **Reset to defaults** restores both groups and the **On my services** view.

Drag the league pills to reorder them (use the grip on touch screens), or expand **League priority** for keyboard-accessible up/down controls. A tap still toggles a league. With AI on, Claude supplies the initial order; with it off, the built-in order (Premier League first). Your services, league selections and priority order are saved automatically in this browser's local storage; reset restores the defaults and that initial order. Each competition you switch on or off is remembered by name, and one you have never set (because it had no fixtures when you chose) follows its default when it appears. League priority runs from 100 for the first league to 0 for the last, evenly spaced over the full list. Filters do not renormalize it. A pick's score is **80% match interest + 20% league priority**, where match interest is Claude's rating and the page's own Outlook score, half each, or the Outlook score alone with AI off or for a match Claude hasn't rated (below, with the settings that tune it). Its score tooltip shows every part.

The default services are HBO Max, Fox One, Paramount+, ESPN Unlimited, Apple TV, USA Network, Prime Video, Netflix and Disney+. All competitions are enabled except Women's friendly, USL Championship, USL League One, NWSL, Eredivisie, Ligue 1, Conference League and Europa League. These defaults are set by `OWNER` and the `LEAGUES` entries marked `default_off` in `build.py`. Saved browser choices take precedence until reset. Matches of the US national teams (`FEATURED_TEAMS` in `build.py`) show by default even in a competition that is off by default, such as women's friendlies; switching that competition off hides them too.

## How it runs

`build.py` uses Python 3.11 or newer and `curl`; `story.py` adds the Anthropic Python SDK. It fetches eleven days of fixtures and the current standings from ESPN's public scoreboard API, maps each listed broadcaster to the streaming services that carry it, applies each competition's usual home when channels are not posted yet (both from `rights.toml`, below), and writes one HTML file. The page's own script does the rest in the browser: bucketing by the viewer's clock, the lineup, filters, the countdown and live scores.

Edit the page structure in `web/page.html`, the styles in `web/styles.css`, and browser behavior in `web/app.js`. The generator reads these files relative to `build.py` and inlines them into the generated HTML, including with `--fragment`. The small document wrapper and reset styles remain in `build.py`. Rebuild after editing an asset; deployment still consists of the generated HTML and optional `story.json`.

The workflow in `.github/workflows/refresh.yml` runs the script three times a day and publishes the page to the `gh-pages` branch, which GitHub Pages serves. It can also be run by hand from the Actions tab (**Refresh outlook**, then **Run workflow**), and it runs on changes to the generator, story script, rights data, `web/`, tests or workflow scripts. The unit tests and the browser checks run first; if either fails, the last good page stays up.

To test and build locally:

```sh
python3 -m unittest -v
python3 build.py --out site/index.html --warnings work/mapping-report.txt
```

Add `--date YYYY-MM-DD` to build as of another day. Open the page with `#at-YYYYMMDD-HHMM` on the URL to preview it as of another local time.

### Browser checks

The optional browser tests use Playwright and Chromium. From the repository root:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r tests/requirements-browser.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python -m tests.browser
```

On Linux, Playwright may also need system libraries (`python -m playwright install --with-deps chromium`). The checks run Playwright's own Chromium, the version it was built against; set `BROWSER_EXECUTABLE` to use another binary. These dependencies are only for testing.

The checks use a synthetic schedule, a fixed clock and local scoreboard responses; they need no ESPN access or API key. They cover lineup persistence/reset, the midnight and 4 a.m. boundaries, live-to-final score updates, failed requests, factual summaries, simultaneous kickoffs, uncertain coverage, and the rolling 24-hour cutoff, later-story fallback, and phrase-level filtering of Claude's text in light and dark themes, keyboard focus through redraws and live updates, the details preview through a live update, league priority from the keyboard, saved settings that are malformed or in an earlier format, the US teams' default, 24-hour clocks, unconfirmed kickoffs, the top card's countdown to the next match on the lineup, its turn to live, and a match finishing while other scoreboard answers are outstanding, the top card's row layout and heading at four widths, the bar staying at the top with the reader's place kept through view changes and keyboard focus kept clear of it, the coffee link's place at three widths, a malformed story, and source labels, the pick score's blend of Claude's rating and the Outlook score with its tooltip, a page with AI off ranking by the Outlook score alone and never asking for storylines, and a card without a blurb showing its details at three widths while rows and a card with a blurb keep theirs in the panel. Match-column alignment is checked at five widths using long team names and different broadcasters. Desktop/mobile screenshots in light/dark themes, with the lineup and match details open, are saved under `work/browser/`. External fonts are replaced with the same fallback fonts for reproducibility. `.github/workflows/browser.yml` runs these checks on relevant pushes and pull requests and saves the screenshots, and `refresh.yml` runs them before every publish: a failing check keeps the last good page up, while a browser that can't be installed or started (a problem with the runner, not the page) publishes with a warning instead. Without a baseline (below) there are no pixels to compare, but every layout must still fit its width.

For a before/after comparison, pass `--baseline-build /path/to/original/build.py` to the browser command. Keep its `rights.toml` beside it, along with `web/` for revisions that use extracted assets. Both generators receive identical fixture data and build time. The comparison requires byte-identical document and fragment HTML and compares screenshot pixels in all 12 viewport/theme/UI combinations, then runs the behavior checks against both versions. Pixel comparisons use pixelmatch's standard antialiasing detection and perceptual threshold of 0.1, since Chromium can paint a few edge pixels differently even for identical pages; any remaining differing pixel fails the check and produces a diff image. Use this when restructuring code without intentional output changes; ordinary browser runs exercise the current version only.

## Live scores

The page is rebuilt three times a day, but scores don't wait for a rebuild. From 15 minutes before a kickoff until ESPN calls the match over, the viewer's browser asks ESPN's public scoreboard for that competition's day once a minute and updates the score, the clock, half time and full time, the scorers, the "Live now" group, the top card (which turns from a countdown into the live score), the picks and the schedule summary. A match that finished since the last rebuild is asked about once when the page opens, so "Earlier today" carries its result.

- **Loading stays fast.** The requests start after the page has drawn, run in parallel (one per competition and day, not one per match), and each is abandoned after 8 seconds. Nothing waits on them.
- **Failing quietly.** A request that fails or times out leaves the page as it was built. After a failure the page waits longer before trying again, doubling up to ten minutes, and Schedule and data details shows when the scores were last checked.
- **Not wasteful.** Nothing is asked while the tab is hidden, while no match is near its kickoff, or for competitions switched off in the filters.
- **Awaiting score, not live.** A match whose kickoff time has passed before ESPN reports it under way is listed under Live now with an "Awaiting score" badge, and the top card, if it holds that match, says the same; only ESPN's word makes it "Live".
- **Testing.** Served from `localhost`, the page accepts `?scoresbase=http://localhost:PORT/some/path/` to read scoreboards from a local stand-in for ESPN instead.

## Keeping the broadcast facts right

Which services carry which channels, the names ESPN uses for each channel, and where each competition usually lives are all in `rights.toml`, each with its source and the date it was last checked. These facts change with every season's rights deals, and sometimes mid-season with a carriage dispute, and ESPN's data shows none of that. Several guards keep a stale or mistaken fact from quietly misleading the page:

- **Tests before every publish.** `tests/test_rights.py` checks that the file agrees with itself (every service names real channels, no two channels claim one ESPN name, every usual home is carried by some service and has a season end, every fact has a source and date, no misspelt keys) and repeats each mistake the page has actually made, from USA Network's "USA Net" to the Bundesliga's move off ESPN. The workflow runs them before building; if they fail, the last good page stays up and GitHub emails about the failed run.
- **Competitions ESPN doesn't list.** ESPN posts no broadcasters at all for some competitions (Liga MX, the Primeira Liga, the Brasileirão, Argentina, the Saudi Pro League) and few for others, so for them `rights.toml` is the only basis. Where one service carries every match, it is the usual home (the Primeira Liga on beIN Sports Connect). Where rights go club by club, `by_home_team` names the usual home for each home club (Liga MX: ViX for TelevisaUnivision's 14 clubs, Peacock for Chivas, FOX for Juárez, Santos and Tijuana); a club it doesn't name claims nothing and is reported. Where no service has every match (Ligue 1, the Saudi Pro League), the page shows a hint instead of a claim.
- **Usual homes lapse.** Each competition's usual home is for one season and lapses after its `until` date. After that the page claims no usual home for it until someone confirms the new season's, because rights change at the turn of a season and a stale claim is worse than none.
- **On my services means available.** Only matches with listed or established usual coverage on a selected service appear in this view. Wholly unconfirmed coverage, unrecognized channels and usual coverage on an unselected service stay under **Everything**. When the next 24 hours has no viewable matches, an explanation appears above the collapsed later schedule.
- **A report, as a GitHub issue.** Each build lists what it couldn't map or vouch for: unknown broadcaster names, a usual home that disagrees with ESPN's listings or lapses within 30 days, and facts unchecked for 180 days. While that list has anything in it, the workflow keeps one issue labelled `mapping` open, mentions you on it, comments when the list changes, and closes it when a build comes back clean.

**To fix an issue:** open the repository in Claude Code and ask it to resolve the open mapping issue. Each item needs some research on the web, then an edit to `rights.toml` with the source and today's date, then `python3 -m unittest`. Pushing to main rebuilds the page and, once the report is clean, closes the issue.

## Scores and the AI switch

`settings.toml` holds what the owner tunes, and each build checks it as it checks `rights.toml`: a misspelt key, a weight below zero, an empty pair of weights or a channel `rights.toml` doesn't know stops the build with every problem listed, and the last good page stays up.

- **The AI switch.** `[ai] enabled = true` lets Claude write the overview and the match blurbs and rate every match (Storylines, below). Set it to `false` and nothing calls the API: `story.py` writes nothing, not even the story already published, so the next build publishes the page without storylines, the page never asks for them, its footer says no AI is used, and picks rank by the Outlook score and league priority alone. To switch, edit the line (GitHub's web editor will do: open `settings.toml`, the pencil, change the word, commit to main); the commit starts a build, so the change is live in a few minutes. Switching back on, that build finds the live page built with AI off and writes the day's storylines at once (one paid run) rather than waiting for the next morning's build. With AI off the page costs nothing to run.
- **The Outlook score.** The page's own interest score, 0 to 100, from ESPN's data alone, the same arithmetic for every match. Five parts, each 0 to 1, combine by weight: the occasion (build.py's stature score: the competition's tier and any marquee clubs or nations, 40%), how evenly matched the betting market sees the teams (the implied chance of a draw, 25%), the stakes (from the table, or a knockout round's stage, 15%), whether a broadcast network or a cable channel carries it (10%) and the goals the market expects (its over/under line, 10%). A part with nothing to go on (no odds, no table, no broadcaster listed yet) counts as one half, so it neither helps nor hurts. The odds are DraftKings' prices in ESPN's scoreboard feed; they shape the score and are never shown. `settings.toml` documents each part and holds every weight and bound.
- **The blend.** Match interest is Claude's rating and the Outlook score in proportion to `[blend] claude` and `outlook` (50 and 50); a pick's score is interest and league priority in proportion to `interest` and `league_priority` (80 and 20). Claude never sees the Outlook score, so each can check the other's leanings: Claude's ratings on 7 October rewarded strong teams more than even matches, which the Outlook score's market part does the other way round. Tuned weights take effect at the next build.
- **Tests don't read it.** The tests render with their own copy of the settings' first values, so retuning a weight or switching AI off can never fail a test and hold up a publish; `tests/test_scoring.py` checks the real file loads, and works each part of the Outlook score out by hand.

## Storylines

When AI is on, once a day, early in the morning, `story.py` asks Claude for a short general overview, one interest-rated paragraph per league, and a rating and sourced blurb for every upcoming match, in two kinds of request (below). The opening shows one overview paragraph, a top card with the match to watch now or next, and up to three highlighted matches with their own blurbs. Each card section disappears when nothing on the lineup qualifies.

- **What Claude gets.** `build.py --facts` supplies upcoming fixtures with a known route through at least one service, including listed channels and the competition's established usual home. Matches with wholly unconfirmed coverage remain under Everything but are not candidates for news. The default lineup and competitions guide the opening; other service choices can reveal different researched items.
- **Two kinds of request.** One research request, with web search and page reads, writes the overview, up to eight match notes, up to three forecast items, a paragraph per league and the league order. Separate rating requests, without tools, about sixty fixtures each and three at a time, return the ratings and card blurbs as structured output. A full run rates every fixture; an update (run by hand) re-rates only what kicks off in the next 24 hours (or has no rating or blurb) and keeps the rest as rated that morning. Rating everything inside the research request made one response of about 40,000 output tokens: it grew with the slate toward the output cap, a gap regenerated all of it, and every refresh re-rated fixtures days away. The research request gets each fixture once, compactly; the ratings get only the fixtures they rate.
- **When it runs.** Once a day. Scheduled builds use `story.py`'s daily mode: the first one of the day (normally the early-morning build, about 4:50 am Eastern daylight time) researches from scratch and rates every fixture, and the midday and evening builds, which still update fixtures, channels and scores, keep that story. If the morning build fails or GitHub never starts it, the next scheduled build writes the day's story instead. Its auto mode also updates the story at midday and in the evening, at the cost of those two runs as well (an update is smaller than a full run: it re-rates only the next 24 hours); switching is one word in `refresh.yml`. A build after a code push republishes the current story without calling Claude. A manual run from the Actions tab (**Refresh outlook**, then **Run workflow**) chooses: update, write from scratch, or keep.
- **Overview and league context.** The overview is one paragraph of at most 450 characters, prioritizing the current day and selected services and competitions. Filtered or expired overview sentences can reveal league paragraphs instead, preferring the next 24 hours and then the nearest later window. Every league with viewable upcoming fixtures has a sourced paragraph available for this fallback. A missing overview or league paragraph triggers one repair request that asks only for what is missing and keeps everything already accepted; a league left out of the order is appended in `build.py`'s order.
- **Ranked recommendations.** A separate candidate list contains every upcoming fixture, including those with unconfirmed broadcasts. Claude assigns independent 0–100 scores for popularity, expected gameplay and competitive impact, using supplied form, tables and stage plus verified research. The combined score uses fixed weights of 25%, 35% and 40%. These are editorial ratings, not outcome probabilities. Scores use an absolute scale across days and competitions; an ordinary fixture does not gain points because the rest of the slate is weak. Missing or invalid scores are rejected, and fixtures left without a rating or blurb are asked for once more, in a request of their own.
- **Top card and top three.** The top card answers "what can I watch now, or next?" among the matches on the selected services and competitions. It is a section of its own, headed **Next up** or **Live now** with a line on how its match was chosen, and laid out like a schedule row given more room: the kickoff and countdown (or the clock and score) in the left column with the league's emblem at its foot, the match in the middle, the broadcaster on the right. When ESPN marks one or more in progress, it shows the one with the highest blended score, live; a scheduled kickoff alone does not qualify. Otherwise it counts down to the soonest confirmed kickoff, however far ahead (days and hours beyond a day, then hours and minutes, then minutes and seconds), choosing by blended score between matches that kick off together. A match whose time is still to be set can't be placed in that order and stays among the picks, as the schedule summary's "Next kickoff" leaves it out. Once a kickoff time passes without word from ESPN, the card keeps that match and says it is awaiting its score, as its schedule row does, until ESPN reports it under way (the card turns live) or the live window closes. "Everything" widens the schedule, not the card. The top three exclude the top card's match, select within the next 24 hours first, fill spare places from successive later 24-hour windows, then display the chosen matches in kickoff order, using blended score to break ties. Other live matches can qualify. There is no minimum score. Fewer than three candidates produce fewer cards. Every match has a pick score, from the Outlook score at least, so the cards are picks with AI off too; only a page built without scores falls back to kickoff order, labelled Upcoming. A card without a blurb (AI off, or a match Claude wrote nothing for) has room for what its Details panel holds, so it shows it: each team's season record beside its place and points, each team's top scorer, and links to ESPN's match page, a calendar entry and the league table in place of the Details button. Schedule rows stay compact and keep those in their Details panel, as does a card with a blurb. Player photos are not shown: ESPN has one for about one top scorer in seven, mostly in MLS and the Eredivisie, which made a photo look like a glitch. Filters, priority changes and completed matches update both sections immediately. Unconfirmed broadcast coverage never qualifies.
- **One match renderer.** `MatchCard` in `web/app.js` owns the schedule, pick and live roles. It hydrates each static row from `build.py` and uses its complete body for every layout: team badges, standings, last-five form, competition, stage, venue, scorers, match news, broadcasters and match details. CSS changes the shape. The live scoreboard updates the canonical row, then refreshes featured views, including clock-only and scorer corrections; an open details dialog remains attached to its original match. This preserves the static schedule before JavaScript loads and avoids maintaining three separate field lists.
- **Details without layout changes.** Hovering over Details opens a floating preview that stays open while the pointer is over it. Clicking, tapping or pressing Enter opens a native modal dialog with the same information and links. Close, Escape or a backdrop click dismisses the dialog and returns focus to the trigger. Neither view expands a card or schedule row.
- **A blurb for every match.** Each rating includes a specific blurb of at most 260 characters (a longer one is trimmed to its last whole sentence) with the reporting it uses, or, when it rests only on ESPN's table, form and stage, a link to that match's ESPN page labelled "ESPN table and form" rather than as reporting. Match cards show the blurb and source links without truncating the text. Existing researched notes and single-match league paragraphs provide a fallback while new data is generated; the browser does not invent editorial copy.
- **Match context, nearby first.** Every item must directly explain an upcoming fixture: stakes, player availability, selection supported by reporting, a relevant matchup, or a scheduling change. An international break can qualify through its effect on a listed fixture; general club news, financial investigations and unrelated managerial controversy do not. When fresh reporting is unavailable, a league paragraph or card blurb can explain a matchup from the supplied ESPN table, form or stage facts; the page then labels it as based on ESPN's table and form. It must still provide useful context for each league without inventing breaking news or merely repeating kickoff times and channels.
- **Tagged phrases and filters.** Overview and league blurbs contain explicit text segments with fixture references. Team, league and broadcaster references come from the schedule rows; they drive filtering without a visible tag list. A blurb disappears when none of its matches has coverage on the selected services and competitions. Within a mixed blurb, excluded phrases are dimmed: removing Apple TV can dim only “MLS” in “MLS and the Premier League.” Neutral connecting words remain unchanged. “Everything” widens the schedule but news still follows the selected services. Match notes follow the same availability rule. Unknown fixture references invalidate an item. The overview, forecast items and match notes must cite a page Claude's searches or page reads returned in that run; league paragraphs and card blurbs may instead rest on ESPN's facts for the fixtures they name. Another fixture's ESPN page, or a page the run did not read, never counts, and text that cites only such pages is dropped.

- **Freshness.** New stories remain eligible through their explicit 24-hour horizon, including across midnight. Completed or elapsed fixtures leave the opening commentary. The page checks for updated story data every ten minutes. Old untagged opening text stays hidden until a research run produces the new format; existing match notes can still appear on their fixture rows.
- **One overview and schedule expansion.** The only standalone blurb is the overview at the top. Neither Next 24 hours nor Beyond 24 hours has an introductory paragraph or generated count sentence; match-specific news stays with that match. Later fixtures open automatically when fewer than five matches are visible in the next 24 hours. A manual close persists through score updates; changes to filters or the sparse/busy threshold apply the appropriate default again.
- **The schedule summary.** Collapsed Schedule and data details in the footer retain factual live/upcoming counts and coverage for the next 24 hours, with the next kickoff and simultaneous matches grouped together. Listed coverage, usual coverage awaiting a listing, unknown coverage, hidden competitions, pending scores and incomplete ESPN requests are distinguished. A later kickoff is explicitly labelled “Beyond 24 hours.” No browser-generated commentary invents a quiet day, an international break or a pick of the week.

- **Model and effort.** Claude Opus 5.5 at medium effort, its own default, for the research and the ratings, in the daily run and in any update run by hand. To change them without editing code, set the repository variables `STORY_MODEL` (`claude-opus-5-5` or `claude-sonnet-5-5`), `STORY_EFFORT` and `STORY_REFRESH_EFFORT` (`low`, `medium`, `high`, `xhigh` or `max`) under Settings, then Secrets and variables, then Actions, then Variables. The **Compare storyline models** workflow in the Actions tab writes today's storylines once per model and effort you list, publishes nothing, and lays the results side by side with their cost, time and sources, so the choice can be made on this page's own evidence. Its **ratings** mode instead asks each configuration for Claude's three scores alone (popularity, expected gameplay and competitive impact) for the fixtures of the next three days, widened a day at a time when they number fewer than 20: no research, no blurbs, no web search, the cheap design and the only one Haiku 5.5 can run. Its summary measures how far the configurations agree with each other, with the ratings published now and with the Outlook score (Spearman's rank correlation with a 95% interval, and the top three each day on the default lineup), next to what each cost.
- **Cost.** Each run logs its token use, searches, time and an estimated cost at list prices on the run's summary page. Rating every upcoming fixture adds input and output tokens, so cost varies with the slate and any repair request. The first full run of the current design (7 October 2026: research plus ratings and blurbs for 315 fixtures, Opus 5.5 at medium effort) took 4 minutes 18 seconds and cost about $1.80 at list prices: 78K fresh input tokens, 53K cache-written, 371K cache-read, 51K output (more than half the cost) and 12 searches. With one such run a day, storylines cost about $55 a month at list prices, plus any run by hand; the size of the slate moves it. Use the reports to set the API workspace's spend limit; a run that hits it publishes without new storylines or ratings.
- **Setup.** Add an Anthropic API key as the repository secret `ANTHROPIC_API_KEY` (Settings, then Secrets and variables, then Actions). Without it, or if a call fails, the page is published as usual without storylines. To turn Claude off, use the switch in `settings.toml` (below) rather than deleting the secret: without the secret the day's story stays up and the page still describes Claude's part.

- Broadcast assignments come from ESPN and can change on the day.
